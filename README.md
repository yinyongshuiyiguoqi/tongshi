# 通事 TONGSHI · 涉外执法现场助手

传智杯参赛作品。民警登录后，用自己的话描述现场情况，系统在情形库里匹配出最接近的一条，
给出处置流程、法律依据、研判要点和可以照着念的话术。

## 运行

双击 `start.bat`，或者：

```bash
npm install
npm run dev      # http://localhost:5180
npm run build    # 产物在 dist/
```

## 现在能做什么

- **登录**：警号 + 姓名 + 单位，会话存在 localStorage，刷新不掉
- **输入**：自由文本，中文口语、错别字都能用；支持浏览器语音输入（Chrome / Edge）
- **匹配**：输入实时比对情形库，给出匹配度、命中的关键词、其他可能情形
- **输出**：处置流程、研判意见、法律依据、现场话术、注意事项、待确认事项
- **兜底**：情形库没命中时交给大模型，在法规要点范围内给出处置思路，并明确标注「未经情形库校验」
- **降级**：匹配置信度低时明确提示，不硬给结论

## 两段式：命中的走库，没命中的走模型

只靠情形库，覆盖面有限；只靠大模型，它会编条号和数额，执法场景里不能用。所以分两段：

| 情况 | 走哪条路 | 特征 |
| --- | --- | --- |
| 命中情形库 | 标准答案 | 流程、依据、话术都是人工核定过的，可追溯，断网可用 |
| 没命中 | 大模型 + 法规要点 | 能给任意描述一个思路，但标注为参考，需人工核对 |

两段共用同一份法规要点。模型那一路的提示词明确禁止编造法名、条号、数额，依据不足时要求直接说明
需要补充什么。这样既保证「任意问题都有回应」，又不至于把编出来的东西当依据用。

## 匹配是怎么做的

`src/lib/match.ts`，两路打分相加：

1. **关键词命中**：每条情形配一组关键词和权重，"拿不出""钱包被偷""喝多了"这类口语说法直接命中
2. **字符二元组相似度**：兜住关键词覆盖不到的表述，容忍口语和错别字

最终分 = 0.85 × 关键词得分 + 0.15 × 形似度。关键词得分做饱和处理，命中越多越高但不逼近满分。
没有关键词命中的条目会被过滤掉，避免仅凭"提到外国人"就匹配到某一条。

现在的结果全在浏览器里算，断网也能跑。接向量检索时把第 2 路换成 embedding 即可，接口不变。

实测六种输入：

| 输入 | 匹配结果 | 匹配度 |
| --- | --- | --- |
| 小区门口一个外国人拿不出护照，只会说英语 | 外籍人员无法出示证件 | 54% |
| 有个老外住在朋友家一个多星期了，一直没去登记 | 外籍人员住宿未登记 | 56% |
| 酒吧门口两个外国人喝多了在闹事 | 外籍人员醉酒滋事 | 69% |
| 签证过期两个月了还在餐厅打工 | 签证过期、非法居留（附：非法就业） | 72% |
| 外国人钱包被偷了，在路边哭，不会说中文 | 求助（迷路、失物、语言不通） | 73% |
| 路口两车剐蹭，一方是外国人，没人受伤 | 涉外交通事故（附：涉外纠纷） | 66% |

## 加一条情形

只需要改 `src/data/cases.ts`，往 `CASES` 里加一个对象：

```ts
{
  id: 'c-xxx',
  title: '情形名称',
  severity: '低' | '中' | '高',
  scene: '一句完整的描述，用于相似度比较',
  keywords: [{ w: '口语说法', weight: 3 }],   // 3 强相关，1 弱相关
  steps: ['第一步', '第二步'],
  provisionIds: ['p-crj71'],                  // 指向 PROVISIONS 里的条目
  scripts: [{ zh: '中文话术', en: '英文话术' }],
  risk: '注意事项',
  brief: '一句研判要点，不要重复流程',
  followUp: '还需要确认什么',
}
```

界面不用动，情形数量、分类列表、匹配全部自动跟上。

## 架构：前端 + Agent 服务

```
浏览器 (React)  ──POST /api/analyse──▶  Node Agent (server/agent.mjs)
                                          │
                                          ├─▶ 元典 law_vector_search（检索现行法条）
                                          └─▶ 大模型（DeepSeek / Claude / 通义，可切）
```

Agent 循环在服务端跑，前端只负责渲染。这样做有三个好处：key 不进 bundle；
MCP 或第三方接口不受浏览器 CORS 限制；中间过程（检索了什么、命中几条）可以推回前端展示，
评委看得见。

跑起来需要两个进程，`start.bat` 会自动开：

```bash
npm run agent   # 8787，Agent 服务
npm run dev     # 5180，前端（已配 /api 代理）
```

服务端读的是**不带 VITE_ 前缀**的变量（`.env.local`）：

```
LAW_API_KEY=...
LLM_API_KEY=...
LLM_BASE=https://api.deepseek.com
LLM_MODEL=deepseek-chat
```

没配 key 也能跑：检索返回示例数据、回答走模板，界面会明确标注，链路本身是通的。

### 为什么不用 Hermes / OpenClaw 当外壳

这两个是本地 Agent 运行时，适合自己用；比赛要求作品是公网可访问的 Web 应用，套上去之后
就没有「在线演示」了。同样的 Agent 逻辑用 90 行 Node 写在 `server/agent.mjs` 里，
评委打开网址就能用，也更容易写进技术文档。

## 接法规检索（可选，但强烈建议）

情形库没命中时，光靠模型容易编条款。接一层真实法规检索能解决这个问题：

`.env.local` 里加

```
VITE_LAW_API_KEY=你的元典开放平台 Key
```

用的是元典开放平台（open.chineselaw.com）的 `law_vector_search`，按自然语言检索法条，
只取「现行有效」的条目，返回法规名称、条号、效力级别和时效性。检索结果会：

1. 直接显示在结果卡里，作为「检索到的依据」
2. 作为提示词上下文喂给模型，模型只能在这些条目范围内说话

没有配 key 时自动跳过这一步，退回本地要点。

**注意**：浏览器直连可能被 CORS 拦。真被拦了，加一层 Vercel Function 转发即可
（`/api/law` → 元典地址），前端改成调自己的域名。这一步需要部署后才能验证。

## 接真模型

默认走本地规则，不连网也能完整演示。拿到 key 后：

```bash
cp .env.example .env.local
# 填 VITE_LLM_BASE / VITE_LLM_KEY / VITE_LLM_MODEL
npm run dev
```

配了 key 之后有两处会变：命中情形时，「研判意见」由模型流式生成（失败回落到 `brief` 字段）；
没命中时，直接给出一段 AI 研判，而不是提示「未匹配」。**不做这一步，任意输入拿不到回应。**

接口按 OpenAI 兼容格式，DeepSeek、智谱、通义、Moonshot 都能直接用。

**安全**：前端直连会把 key 打进 bundle。仓库只提交 `.env.example`，真 key 放 `.env.local`
（已在 `.gitignore`）；正式上线要加后端代理。

## 登录

不是摆设。账号写在服务端（`server/agent.mjs`），前端只拿到 HMAC 签名的会话令牌，
12 小时过期；`/api/analyse` 会校验令牌，没有令牌直接 401。

演示账号：警号 `100234` / 密码 `tongshi`（另有 100235、100236 两个）。

正式环境应换成内网统一认证，会话密钥走 `SESSION_SECRET` 环境变量。

`showcase.html` 是单独一个入口，用苹果购买页那套语言讲作品：大标题、灰底圆角块、
底部吸附条。录演示视频和答辩时用，不影响应用本身。

```
http://localhost:5180/showcase.html
```

## 打印与导出

结果卡上有“打印 / 存为 PDF”。用的是浏览器原生打印，配了一套打印样式：只输出结果卡，
隐藏输入区、导航和按钮。在打印对话框里选“另存为 PDF”即可归档。

## 必须处理的两件事

1. **法条要核**。`PROVISIONS` 里的 `summary` 是要点摘录，不是条文原文，条号也要对着现行文本逐条核。
   评审抽查依据时这里出错是硬伤。建议换成带原文和生效日期的 JSON。
2. **情形库要扩**。现在 9 条，覆盖常见涉外警情，但远不够。扩到 30 条左右，
   匹配质量会有质的提升，也是最容易加分的活。

## 已知限制

- 匹配是字面匹配，"对方不肯配合"这种抽象表述容易漏
- 情形之间没有冲突消解，输入同时命中多类时只按分数排序
- 语音输入依赖浏览器能力，Safari 表现弱
- 没有后端，登录不做真实校验
